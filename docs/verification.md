# Verification

What was checked, how and when, phase by phase. The README states only what this page shows, or says "expected" and why.

| # | Check | Phase | How | Result |
|---|---|---|---|---|
| V1 | Private endpoints and the internal web app resolve to private addresses on the jumpbox | 1 | `az vm run-command` on the jumpbox (no Bastion or internet needed): `getent hosts`, `curl`; the same from the laptop | **verified 2026-11-16:** on the jumpbox, Key Vault resolves to its private endpoint (10.40.2.4) and answers a token of the VM's identity with `ForbiddenByRbac` (the network lets it through; the identity has no role); the web app resolves to the environment's static IP (10.40.3.17) and answers 200 (23 s while it scales from zero, then 27 ms); the internet is unreachable (no NAT Gateway outside sessions). From the laptop, the web app's name doesn't resolve and Key Vault refuses a signed-in request: "Public network access is disabled". |
| V2 | The jumpbox has no public IP and accepts SSH from the Bastion subnet only | 1 | the NIC and the network security group's rules | **verified 2026-11-16:** no public IP on the VM (`az vm show -d`); inbound rules: SSH from 10.40.0.0/26 (the Bastion subnet), then deny all; the subnet is private (no default outbound access). |
| V3 | Creating a Bastion Standard host with its NAT Gateway, and deleting both: durations | 2 | `make bastion-up` / `bastion-down`, timed, and the activity log | **verified 2026-11-16:** the host took 9 min 47 s to create (activity log: write accepted 19:46:48, succeeded 19:56:35 UTC); the NAT Gateway, the jumpbox's start, its Entra SSH extension and tools fit in that time. Deleting the host took 476 s (about 8 min). A session therefore costs about 18 minutes of waiting, and the host is billed for that time too. |
| V4 | SSH from the laptop with Entra ID (`az network bastion ssh --auth-type AAD`), no SSH key | 2 | `make bastion-ssh`, and the same command with a remote command | **verified 2026-11-16:** signed in as the Entra user in 11 s; the `ssh` extension generated a certificate valid about an hour; on the jumpbox, Key Vault resolves to its private endpoint. Needed the laptop's `bastion` and `ssh` CLI extensions reinstalled (a compiled module no longer loaded after a CLI upgrade). |
| V5 | The tunnel, VS Code Remote-SSH, file transfer | 2 | `make bastion-tunnel` (writes `.ssh/config` with an Entra certificate), then `ssh -F .ssh/config jumpbox`, `scp` | **verified 2026-11-16:** the tunnel opened in about 4 s; `ssh` signed in with the Entra certificate in 2 s with no prompt (`BatchMode`), and `scp` copied a file. **2026-11-17:** VS Code Remote-SSH (1.146, Remote-SSH 0.128) opened a terminal on the jumpbox as the Entra user, from VS Code in WSL with that configuration, and from VS Code on Windows with Windows' own OpenSSH and a copy of the key and certificate (the tunnel's port on WSL's localhost reaches Windows). Pointing Windows VS Code at WSL's `ssh` (`remote.SSH.path`) failed: with WSL in NAT networking mode, the dynamic forward it opens in WSL refused the editor's connection from Windows (`ECONNREFUSED`). |
| V6 | `ssh -L` to Key Vault's private endpoint, `ssh -D` with `socks5h` for a browser, `curl`, the Azure CLI and `kubectl` | 2 | `ssh -F .ssh/config -N -L 8443:<vault>:443 -D 1080 jumpbox`, then each client | **verified 2026-11-16:** through `-L` (with `curl --resolve`) and through the SOCKS proxy (`--socks5-hostname`), Key Vault answers 401 (reached, unauthenticated) where the direct path is refused; the private web app answers 200 through the proxy and not at all without it. The Azure CLI lists the vault's secrets with `HTTPS_PROXY=socks5h://127.0.0.1:1080` (all traffic, or only Key Vault with `NO_PROXY` for sign-in and management). `kubectl` reaches a private name through `proxy-url: socks5://127.0.0.1:1080` in its kubeconfig (resolved on the jumpbox), and fails with the proxy closed. **2026-11-17:** a browser through the same proxy: Microsoft Edge on Windows, started with its own profile and `--proxy-server=socks5://127.0.0.1:1080` (names resolved by the proxy), showed the private web app's page. VS Code's built-in browser needs VS Code itself started with that option; not checked (the window opened inside the running VS Code, without the proxy, and the name didn't resolve). |
| V7 | The reaper's least-privilege role suffices to delete a host and its NAT Gateway and to deallocate the jumpbox | 3 | the function's logs and the activity log | **verified 2026-11-17**, after one change to the role: deleting the host worked first time; detaching the NAT Gateway from the jumpbox subnet was refused (403 `LinkedAuthorizationFailed`): a subnet write also needs `Microsoft.Network/networkSecurityGroups/join/action` on the subnet's network security group ([D10](DECISIONS.md)). With it, the reaper detached and deleted the NAT Gateway and deallocated the jumpbox. Nothing else was refused. |
| V8 | The reaper deletes an expired host within 15 minutes, spares an extended one, and deletes an untagged one | 3 | two sessions, the function's logs | **verified 2026-11-17:** session 1, `delete-after` 10:10 UTC: kept by the 10:00 run, deleted by the 10:15 run (7 min 55 s). Session 2, created with an end at 11:49, moved to 12:20: kept by the 12:00 run. Its tag then removed: the 12:15 run deleted the host (9 min 35 s), detached and deleted the NAT Gateway (15 s) and deallocated the jumpbox (31 s), 622 s in all. Runs with no session take 1 to 3 s. |
| V9 | The cost of a session and of an idle day | 4 | Cost Management, by resource type and day, 16 to 18 November (billed in USD at the subscription's own rates) | **verified 2026-11-19:** an **idle day** (18 November: no session, jumpbox deallocated, sample targets deployed) cost $1.02: $0.36 Microsoft Defender for Storage on the reaper's account (a plan of the subscription, not part of the sample), $0.24 the two public IPs, $0.24 the Key Vault private endpoint (sample targets), $0.09 the jumpbox's disk, $0.04 Log Analytics, $0.02 the reaper's function app, $0.03 the rest; without the sample targets and Defender, about $0.40 a day. **Sessions:** on 16 November, one session (host from 19:47 to 20:51 UTC) cost $0.23 for the Bastion host and $0.08 for the NAT Gateway; on 17 November, the sessions' hosts cost $0.28 and their NAT Gateways $0.18. The jumpbox added $0.66 and $1.56 on those days, running beyond the sessions while the sample was built. |
| V10 | A resource in a peered virtual network, behind a private endpoint with its own private DNS zone, is reachable from the jumpbox ([peering guide](peering.md)) | 4 | a test network `10.50.0.0/16` with a storage account (public access disabled, blob private endpoint, its own `privatelink.blob.core.windows.net` zone); `az vm run-command` on the jumpbox before and after | **verified 2026-11-17:** before: the name resolved to a public address and the account refused the request (403). After peering both ways (`Connected`, `FullyInSync`) and linking the zone to the sample's network: the name resolved to the private endpoint (10.50.0.4) and the account answered the anonymous request with 409 "Public access is not permitted on this storage account". Linking a second `privatelink.vaultcore.azure.net` zone to the sample's network while its own existed was refused: "A virtual network cannot be linked to multiple zones with overlapping namespaces". The test network was deleted. |
| V11 | With `DEPLOY_SAMPLE_TARGETS` off, only the targets go; with it on, an existing deployment keeps them | 4 | `azd provision --preview` both ways on the deployed environment | **verified 2026-11-17:** on: 9 resources moved, 0 to add, change or destroy; off: the 12 target resources (web app, environment, its DNS zone, record and link, Key Vault, its private endpoint and role, the vault's DNS zone and link, the Container Apps subnet) to destroy, nothing else. |
